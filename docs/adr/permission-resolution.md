# Permission resolution

## החלטה

`AccessLevelAssignment` הוא מקור האמת היחיד להרשאות עסקיות. הטבלאות `UserPermissionAssignment` ו־`GroupPermissionAssignment` נשמרות זמנית כנתוני Legacy לצורכי שחזור ותאימות migration, אך אינן נקראות על ידי מנוע ההרשאות. `RolePermission` אינו משתתף בפתרון הרשאה: תפקיד הוא הקשר עסקי של משתמש בתוך Environment, בעוד שקבוצה היא מקור ירושת הרשאות.

## מודל

- משתמש יכול להשתייך למספר קבוצות פעילות. קבוצה לא פעילה אינה תורמת הרשאות.
- Assignment שייך למשתמש או לקבוצה, לעולם לא לשניהם.
- רמות הגישה הן `none`, `view`, `edit`; בתוך שכבת קבוצות נבחרת הרמה הגבוהה ביותר.
- היעדר Assignment אישי משמעו ירושה ואינו נשמר כרשומה.
- התחולה היא כללית או Environment מסוים.

## סדר קדימויות

1. חריגת משתמש בסביבה.
2. הרשאות קבוצות בסביבה.
3. חריגת משתמש כללית.
4. הרשאות קבוצות כלליות.
5. ברירת מחדל `none`.

השכבה הראשונה שקיימת מחליפה שכבות כלליות יותר. `is_system_admin` מחזיר `edit` בכל Domain, אך אינו עוקף Authentication, Audit, Approval Task או כללים עסקיים.

## הסבר הרשאה

`EffectivePermissionService` מחזיר לכל Domain את הרמה האפקטיבית, סוג ושם המקור, התחולה ושלבי ההכרעה. אותו Service ממפה את הרמה ל־permission codes הפנימיים שבהם משתמשים ה־routes. אין לכתוב resolver נוסף בתוך route.

## דוחות ופיצ'רים עתידיים

לכל דוח Domain נפרד (`report_cases`, `report_audit`, `report_sla`) ו־capability פנימי נפרד. פיצ'ר חדש שדורש הרשאה חייב להוסיף Domain בעל קוד יציב, שם ותיאור בעברית, קטגוריה ו־Scope; להציגו בעורכי משתמשים וקבוצות; לאכוף אותו בשרת; לבדוק אותו; ולהוסיף אותו להסבר האפקטיבי.

## Migration ותאימות

Migration `0013` מוסיפה קטגוריה, אינדקסים ייחודיים לרשומות כלליות ומבצעת backfill הן מהטבלאות הישנות והן מ־Access Domains שהוחלפו. נתוני Legacy אינם נמחקים או נדרסים. לאחר אימות שאין צרכנים חיצוניים ניתן להסיר את הטבלאות הישנות ב־migration עתידית נפרדת.
